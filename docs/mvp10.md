# MVP 实验安排

**默认流程是发送题目、保存回答、按规则评分。** Harbor 和 Docker 均非必需，模型无需写文件或调用工具。设计依据见[提案](proposal.md)，采样步骤见[试验流程](pilot-protocol.md)，出题前提见[出题规则](task-design-rules.md)。

当前有哪些题、各自什么版本、跑没跑过：

```bash
python3 scripts/status.py
```

## 版本边界

每道题带自己的 rubric 版本，判分材料随版本走，不混用：

| 版本 | 查的项 | rubric | 评审指令 |
|---|---|---|---|
| v0.2 | S1–S4 | [rubric v0.2](rubric.md) | [v0.2 评审指令](../graders/strict-editor.md) |
| v0.3 | S1–S7，新增 S5 夸大意义、S6 装深刻的结尾、S7 故作洞见 | [rubric v0.3](rubric-v0.3.md) | [v0.3 评审指令](../graders/strict-editor-v0.3.md) |

不得把旧回答直接改称新规则下的独立测试结果。不同版本的结果不得混算成同一次提示干预。

## 判分

strict-v1 对任意一处确认的风格或交付问题都判整题失败，`reward = 0`。其他内容正确不能抵消失败。没有失败但仍有未裁定项时，结果为未裁定；只有全部必查项明确通过，才给 `reward = 1`。

主要目标不限制检查范围：一道题主攻 S5，出现 S2 或 S3 仍须判分。近义改写、拆句、换序不自动获得豁免。规则也不能误伤源事实，必要否定、具体好处、真实感受和正常礼貌应按题目保留。

## 每份回答要记的

| 字段 | 要求 |
|---|---|
| 题目与版本 | 题目 ID、完整输入、共用指令、条件提示、rubric 与判分政策版本 |
| 生成设置 | 模型完整标识、日期、调用方式、推理档位、可控参数、输出上限 |
| 可见上下文 | 系统与开发者指令、工具设置、未知或不可控设置 |
| 原始输出 | 首次回答全文、尝试编号、运行次序、完成状态 |
| 评分证据 | 该版本全部风格项、原文片段、例外依据、保真与可用性、审核者和分歧 |

普通聊天界面中无法取得的参数标为未知。隐藏系统提示时，A 只能写“未额外添加去套话提示”，不能声称已排除所有风格指令，更不能据此推断模型未受过去套话训练。[评分校验脚本](../scripts/score_review.py)同时支持 v0.2 和 v0.3，但不替评审判断句子的意思。

网络或服务故障单列，不算风格失败；重试保留记录。空答和未完成的回答也要记录。

## 后续扩题

先用现有题检查诱发效果、评分边界和 B 的副作用。若 A 经常写得简洁，照实报告；不能把正常请求改成精确字数或逐字复制陷阱来制造低分。

后续任务继续从 skills 的具体模式选择自然场景，每题须有事实清单、失败依据、合理对照和完整参考答案。选定题集后冻结，再采样验证。编写好的校准片段不能支持“模型普遍低于 20%”或“接近 0% pass@1”这类结论。

## 旧任务用途

`tasks/` 中的十道旧题保留为明确约束下的诊断材料：`contrast-release-note`、`contrast-correction`、`protected-quote`、`refund-no-new-promise`、`handover-keep-list`、`rollback-plain-paragraph`、`incident-uncertain-cause`、`query-result-no-fluff`、`mentor-email-keep-thanks`、`status-update-multi-step`。

`dataset.toml`、`shared/` 和旧运行脚本服务于这些任务。它们的 oracle、自检和得分只验证当时声明的规则，不能证明当前自然写作题有难度。重放说明见[历史审计](audit-2026-09-19.md)。Harbor 可作调度适配，框架本身不是实验要求。
